# DEVLOG #20

Today I finally found why the four RX streams kept disagreeing: the server was
fusing packets from different transmitter moments. The old path had already
reached `98,126` engine errors with a timestamp spread of about `710 ms`.

The first timing fix exposed the deeper problem. The server was simply taking
the latest packet from each receiver, even when those packets did not belong to
the same event. I replaced that with bounded per-RX queues and approximate-time
matching in both the governed trust path and the public person-count path. The
existing `60 ms` guard stays fail-closed, so an incoherent quartet is discarded
instead of becoming a fake D6 input.

The new tests cover packet loss, reboots, sequence wrap, clock jumps, queue
matching, host-time fallback, clearing pre-reset queue frames, rejecting stale
queue entries after an outage, and selecting the newest coherent set for the
public fuser. The full run has `487/488` passes in the sandbox; the remaining
local-socket test also passes with the required permission (`488/488` across
the two runs). The release build succeeded and the Setup-v2 seal continues to
match the release binary.

The final live restart was blocked by the host usage limit, so no new
calibration or blind result is claimed yet.

Suggested image: a side-by-side status view showing the old timestamp spread
and error counter next to the new timestamp-basis and queue diagnostics.

Next: restart the server and verify a stable, error-free `25-second` preflight.

## Remaining live gates

The release can be verified offline, but the final evidence still needs one
fresh server run. The old process is stopped and its capture remains
diagnostic-only; no old calibration or blind result was reused.

The live sequence is deliberately narrow:

1. Start the final binary with
   `private/d6-20260830-grid64-mmwave-timestamp-fix/sealed-setup-final.json`.
2. Observe all four RX nodes for at least the sealed 25-second preflight. Keep
   host-arrival time, mesh time, sync age/sequence, CSI sequence, loss, FPS,
   timestamp basis, spread, and `total_engine_errors` in the evidence.
3. Accept only if all four RX are fresh, the hard spread stays below `60 ms`,
   and the engine-error counter is constant. A warning rate limit is not a
   substitute for the counter check.
4. Only after that window, reset/stop any contextless collector state and start
   a new empty-room run from the sealed setup. The collector's start gate also
   requires a fresh radar stream, no recent radar sequence fault or reboot, a
   stable CSI-v2 clock epoch, and all four RX preflight windows.
5. Mark the resulting calibration valid only with its newly issued calibration
   ID and matching context hash (`profile context + setup ID + setup SHA-256`).
   Interrupted or legacy manifests remain non-valid evidence.

The final server start was attempted but rejected by the host usage limit. No
live acceptance, collector reset, or new calibration is therefore claimed yet.

Additional fail-closed guards now remove per-RX queue samples older than the
active 10-second host-monotonic window and prevent the public person fuser from
falling back to latest-only selection once live CSI queues exist. This prevents
a long outage from replaying pre-outage CSI and keeps both fusion paths on the
same timestamp-coherence rule; the regression tests pass.

After this offline verification, three read-only requests to the previously
