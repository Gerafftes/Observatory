## 2026-08-29 — Stabilisation implementation

I implemented the backend-first stabilisation plan. The mmWave receiver now
separates raw UDP transport from accepted radar content, exposes categorised
rejects, the last rejection, sequence-gap timing, duplicate/discard counts,
queue pressure, and receive-to-process delay. Invalid target coordinates never
become calibration labels, while a valid transport packet keeps the stream
fresh independently of target content.

I added ESP status diagnostics with configuration flags, reachability,
timeout/HTTP/invalid-JSON classification, last-success age, and no token
logging. Session start is transactional: the node mode, fresh expected-mode
packet, diagnostics progression, and full preflight must pass before recording
files are created. Session manifests are durable; active manifests become
`interrupted` after a server restart, and flush or file errors remain visible
instead of disappearing.

I updated the UI so action errors such as HTTP 409 are not erased by status
refreshes. Active stale sessions remain visible with an explicit radar-stream
interruption message, interrupted sessions are shown without auto-resume, and
preflight blockers use readable labels plus transport evidence.

The targeted verification passed: 28 mmWave Rust tests and 22 UI tests. The
local browser surface also renders the new diagnostics and blocker labels. No
new empty-room calibration or blind result is claimed: the live server still
needs to be rebuilt/restarted with valid node URL/token configuration, then a
fresh loss-free preflight and at least a complete 60-second empty-room capture
must be verified from the new manifest and packet diagnostics.

Next: rebuild the server, verify `/api/v1/mmwave/status`, run the complete
